# 0007: Recoverable Final GameReview Independent of the Live Table

Reviewed against the frontend implementation on 2026-11-10.

When a match ends, the frontend saves the completed public game snapshot (`PublicGameStateResponse` with non-null `gameEnd`) in the browser tab's `sessionStorage` inside a versioned wrapper (`PersistedGameEndEnvelope`) tied to the player's `roomId`, `playerName`, and `token`. If the player refreshes the page after the match ends, the app restores the post-game review screen (`GameReviewView`) directly from this saved wrapper—even after the backend server has cleaned up and deleted the finished room.

If the tab does not have a saved `PersistedGameEndEnvelope` yet and the live room or game endpoints return `403` or `404`, `sessionSync` checks the backend's `/api/game/{gameId}/review` endpoint before assuming the session is lost. Similarly, if a "claim win" request times out or drops, the client polls the review endpoint a bounded number of times instead of re-sending duplicate claim mutations. Once a completed `PublicGameStateResponse` (`gameEnd != null`, from a claim response, the `/review` endpoint, or a `/game/{gameId}` WebSocket broadcast) is received, `GameSession` locks in the game-over screen and cancels any in-flight live table recovery.

`PersistedGameEndEnvelope` stores only the final match state and standings (`PublicGameStateResponse` with `gameEnd`), not a hand-by-hand replay history. Checking that `roomId`, `playerName`, and `token` match prevents an old match result from showing up if the tab joins a new game, and the `version: 2` field lets app updates safely discard incompatible cached data (including legacy `version: 1`, unversioned `sessionStorage`, and `localStorage` entries).
